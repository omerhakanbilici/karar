# Karar — bump the bundled Ollaya to v0.7.1

Status: approved in brainstorming on 2026-09-26. Main spec: [`2026-09-24-karar-design.md`](2026-09-24-karar-design.md).
Karar release: **v0.2.0** (build 5).

## 1. Why now

Ollaya v0.7.1 (2026-09-26) runs `laya:en`, `laya:multilingual` and `nli:modernbert-large` on the
Apple GPU through MLX. Measured on this Mac (M1 Pro, 32 GB) with the v0.7.1 binary inside a
Hardened Runtime, ad-hoc signed test bundle, warm, triage preset (5 questions), median of 5:

| Model | CPU (v0.7.1, old manifest) | Apple GPU (v0.7.1, with arch layer) |
|---|---|---|
| `laya:en` | 1141 ms | 166 ms |
| `laya:multilingual` | 419 ms | 61 ms |

Cold load on the GPU: ~1.0–1.3 s. This replaces the 0.4–1.3 s in the roadmap's Phase 2 latency note (main spec §9 risk 3). The README screenshots
show ~1.45 s (warm) and ~4 s (cold), so they have to be retaken.

## 3. Engine and packaging

### 3.1 `scripts/fetch-ollaya.sh`

- `OLLAYA_VERSION=v0.7.1`.
- Two archives, each checked against its sha256 from the release's `sha256sum.txt`:
  - `ollaya-darwin-arm64.tgz`: `e0b281036611f8a074e07ce553a57916bf49c48b609601adec03531ad821942c`
  - `ollaya-darwin-arm64-mlx.tgz`: `5a85d974ade710b9c3c201c73a96eb0bfdbf782d9bf0b0c970cd187f5e619e4f`
- Both unpack into `vendor/ollaya` (same prefix layout: `bin/`, `lib/ollaya/`, `share/`). `VERSION`
  is written last, as now, so a half-done fetch is retried.

### 3.2 Embed script (`project.yml`, "Embed Ollaya")

- `bin/ollaya` → `Contents/MacOS/ollaya`, signed as today (`--options runtime`, identifier
  `io.github.omerhakanbilici.karar.ollaya`). **No new entitlements.** MLX needs none (tested).
- `lib/ollaya/mlx_metal/mlx.metallib` → `Contents/Resources/mlx_metal/mlx.metallib`. That is the
  runner's third lookup path (`<exe dir>/../Resources/mlx_metal/`, upstream's "macOS app bundle"
  case), so Karar sets no `OLLAYA_LIBRARY_PATH`. The metallib is data: the app's signature seals it.
- Notices into `Contents/Resources/Ollaya/`: only regular files from `share/doc/ollaya/` (`LICENSE`,
  `THIRD_PARTY_NOTICES`, `onnxruntime-ThirdPartyNotices.txt`), plus
  `share/doc/ollaya/mlx_metal/THIRD_PARTY_NOTICES` renamed to `mlx-THIRD_PARTY_NOTICES`.
  `llama.cpp-THIRD_PARTY_NOTICES` is left out with the libraries it covers.
- `lib/ollaya/llama/` is not copied.

### 3.3 llama.cpp is not embedded

- With Hardened Runtime, library validation refuses the ad-hoc signed llama.cpp dylibs
  (`dlopen failed`, tested). Loading them would need
  `com.apple.security.cs.disable-library-validation` on the nested `ollaya`.
- The only GGUF models are `winnow` (8–12 GB). They are not in the catalog, and upstream has not
  checked them on Metal yet.
- Effect: a GGUF model pulled with the CLI fails to load in an engine that Karar started. An adopted
  CLI or Ollaya.app engine still runs it. The plan records the engine's exact error text here and in
  the main spec §1.
- Revisit when Karar moves to Developer ID signing: a team ID makes library validation pass.

### 3.4 About and licences

- About gets one more Ollaya row: "MLX notices" → `Ollaya/mlx-THIRD_PARTY_NOTICES`.
- `THIRD_PARTY.md` and `NOTICE`: MLX 0.32.2 and mlx-c (MIT, with {fmt}, nlohmann/json, PocketFFT,
  metal-cpp) inside the bundled engine.

## 4. Existing installs move to the GPU on their own

Models pulled before this release have no `arch` layer and stay on the CPU. A re-pull downloads
only that layer (0.6 s for `laya` with both targets, tested) and does not re-hash the weights.
Karar shows no Download button for an installed model, so it does the re-pull itself.

- **When:** after `connect()` finishes, once the model list is known, as a background task.
- **What:** one pull per installed model from a fixed list: `laya:en`, `laya:multilingual`,
  `nli:modernbert-large`. The router `laya:latest` needs no pull of its own: its targets are listed
  in `/api/tags` themselves.
- **Once:** when every pull succeeds, or when none of the listed models is installed, Karar sets a
  `UserDefaults` flag, keyed by the model store (`gpuRefresh:<OLLAYA_MODELS or "default">`, because
  every Karar build shares one defaults domain), and never runs the refresh again. On failure
  (offline, registry error) the refresh is silent, sets no flag, and runs again at the next launch
  or engine restart. Models downloaded later already come with the layer.
- **No UI:** the refresh does not touch `downloads`, the download sheet or onboarding.
- **Then:** Karar calls `preload()` again. On the next load the engine picks up the new manifest
  and loads the model on MLX (tested: a CPU runner loaded before the re-pull did not block this).
- **Known ceiling:** the runner loaded on the CPU before the refresh stays in memory until its
  `keep_alive` (30 min from preload) ends. This happens once per install. Mark it with a
  `ponytail:` comment.
- **Adopted engines:** the refresh runs only when the connected engine is Ollaya 0.7.1 or newer
  (`/api/version`). An older adopted engine (e.g. Ollaya.app v0.5.0) might not store the layer, so
  Karar skips the refresh and sets no flag; it runs the next time Karar connects to a 0.7.1+
  engine, e.g. its own.
- **Testing:** an `AppModel` unit test with fake `tags`/`pull` and a throwaway `UserDefaults` suite:
  - only listed, installed models are pulled;
  - the flag is set only on success (or when there is nothing to pull);
  - with the flag set, nothing is pulled;
  - a failed pull leaves the flag unset;
  - an engine older than 0.7.1 pulls nothing and sets no flag.

- The other five entries are unchanged.
- Licence and languages of the three new entries come from their pulled license layer and the
  upstream family docs. The plan checks them; nothing is guessed.
- Each new model is pulled into a scratch store and answers all five presets and one custom
  question set through Karar's own engine. Its warm latency on this Mac goes into the roadmap notes.
  All three run on the CPU on a Mac.
- Summaries say it where it helps the choice: `von` reads long text, and `kev` and `decision` are
  slower.
- The new entries use explicit tags so that an upstream alias move cannot change what Karar
  downloads (it happened to `kev` on 2026-09-27). Laya's sizes changed on 2026-09-27 with upstream's
  v0.7.3 registry update (CPU graphs); the silent refresh (§4) then also fetches those graphs, a few
  MB.

## 7. Verification

1. `xcodebuild … test` passes, including the new refresh test.
2. `scripts/smoke.sh` gains one check: after the decide, `/api/ps` lists `laya:en` with
   `device == "metal"`. This guards the metallib's place in the bundle for every future bump.
3. The Release build:
   - `codesign --verify --deep --strict` passes;
   - `Contents/MacOS/ollaya` shows `flags=…(adhoc,runtime)`;
   - `vtool -show-build` shows `minos 14.0`;
   - `Contents/Resources/mlx_metal/mlx.metallib` exists.
4. `scripts/make-dmg.sh`: the DMG size is recorded (expected ~60 MB).
5. The refresh end to end: copy an old store (manifests without `arch`), launch Karar with
   `OLLAYA_MODELS` pointing at it, then check that `/api/ps` shows `metal` and that the manifests
   now carry the layer. Relaunch: nothing is pulled.
6. A GGUF load in Karar's engine: record the error text (§3.3). Use the smallest way to trigger
   it; a winnow pull is 8 GB, so pulling it is not required.
7. UI tests (local, `KararUITests`) pass.
8. Screenshots: retake `docs/screenshots/main-{light,dark}.png` and `advanced-{light,dark}.png`
   with the model warm on the GPU, so the answer time reads in ms.
9. The user confirms the built app. Tag `v0.2.0`, push and release only with the user's explicit OK.

## 8. Out of scope

- The `agent` preset: it needs JSON state `{request, command}`; Karar sends text.
- `qwen3guard`: it answers only its built-in questions, and Karar always sends questions.
- `winnow` and llama.cpp (§3.3).
- `kev:4b` (9.5 GB) and `kev:9b` (19.5 GB). v0.7.1's MLX layouts are ModernBERT encoders only
  (`laya-markers-v1`, `nli-pairs-v1`, `gliclass-uni-v1`), so Kev runs on the CPU on a Mac, with 8.5
  and 16 GB of weights in memory. Reconsider at a later pin if Ollaya moves Qwen3.5 to MLX.
- A UI to update installed models, and showing the compute device (`metal`/`cpu`) in Karar.
